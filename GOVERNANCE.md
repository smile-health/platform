# SMILE Platform Backend Governance

This document outlines the governance model for the SMILE Platform Backend project.

## Project Overview

SMILE Platform Backend is an open-source backend platform built with Node.js, TypeScript, and modern web technologies. It is licensed under the GNU Affero General Public License v3.0 (AGPL-3.0).

## Project Leadership

### Project Maintainer
- **Arya** - arya@badr-interactive.com
- Role: Project lead and primary maintainer

### Core Team
The core team consists of active contributors who have demonstrated:
- Consistent high-quality contributions
- Understanding of the project architecture
- Commitment to the project's success

Core team members are invited by the project maintainer based on their contributions and commitment.

## Roles and Responsibilities

### Project Maintainer
- Overall project direction and strategy
- Code review and merge decisions
- Release management
- Community management
- Security oversight

### Core Contributors
- Code review and quality assurance
- Feature development
- Bug fixes and maintenance
- Documentation improvements
- Mentorship of new contributors

### Contributors
- Submit pull requests
- Report issues
- Improve documentation
- Participate in discussions

## Decision Making Process

### Technical Decisions
- Day-to-day technical decisions are made by contributors submitting pull requests
- Significant architectural changes require discussion in issues or pull requests
- The project maintainer makes final decisions on controversial matters

### Process Changes
- Changes to development processes require:
  1. Opening an issue describing the proposed change
  2. Community discussion for at least 7 days
  3. Approval by the project maintainer

### Governance Changes
- Changes to this governance document require:
  1. A formal proposal issue
  2. Community discussion for at least 14 days
  3. Approval by the project maintainer and majority of core team

## Contribution Guidelines

### Becoming a Contributor
Anyone can contribute by:
- Submitting pull requests
- Reporting issues
- Improving documentation
- Participating in discussions

### Becoming a Core Team Member
Core team membership is based on:
- Sustained, high-quality contributions over 3+ months
- Demonstrated understanding of project goals
- Active participation in code reviews
- Mentorship of other contributors

### Maintainer Selection
New maintainers may be added when:
- The project requires additional maintainers
- A core team member demonstrates exceptional commitment and expertise
- There is consensus among existing maintainers

## Code of Conduct

All participants must follow our [Code of Conduct](CODE_OF_CONDUCT.md). Violations are handled according to the enforcement guidelines outlined in that document.

## Release Process

### Release Cadence
- Major releases: As needed, with at least 30 days notice
- Minor releases: Monthly or as features are ready
- Patch releases: As needed for critical fixes

### Release Responsibility
- The project maintainer is responsible for releases
- Core team members may assist with release preparation
- Security releases follow the [Security Policy](SECURITY.md)

## Community Management

### Communication Channels
- Issues and Pull Requests: For technical discussions
- Email: arya@badr-interactive.com for project inquiries
- Documentation: In the `adr/` directory for architectural decisions

### Meetings
- Ad-hoc meetings as needed for major decisions
- All decisions are documented in issues or pull requests

## Conflict Resolution

### Disagreements
1. Discuss in the relevant issue or pull request
2. If unresolved, escalate to the project maintainer
3. The maintainer's decision is final

### Code of Conduct Issues
Follow the reporting process in the [Code of Conduct](CODE_OF_CONDUCT.md).

## Financial Matters

### Funding
The project accepts:
- Corporate sponsorships
- Individual donations
- In-kind contributions

### Expense Management
- Project maintainer oversees expenses
- All financial decisions are documented
- Annual financial report is published

## Transparency

### Public Information
- All discussions are in public issues and pull requests
- Meeting notes are published when applicable
- Financial reports are published annually

### Private Information
- Security reports are handled privately per the [Security Policy](SECURITY.md)
- Personal information of contributors is kept confidential
